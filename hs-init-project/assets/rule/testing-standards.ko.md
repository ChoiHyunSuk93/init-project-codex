# 테스트와 검증 규칙

## 확인된 검증 진입점

- `HS_INIT_SEMANTIC_TODO`: 실제 manifest, task, CI 또는 기존 문서에서 확인한 unit/integration/E2E/build/lint 명령과 적용 범위를 기록한다. 추측 명령은 기록하지 않는다.

## 선택 기준

- 저장소에 이미 있는 테스트 구조, naming, 명령, framework를 우선한다.
- 변경을 안정적으로 검증하는 가장 작은 테스트 계층을 선택한다.
- 의미 있는 업무 규칙, 권한, 데이터 무결성, 상태 전이, 실패 처리, 외부 연동과 고위험 회귀를 우선 보호한다.
- type, lint, framework 또는 데이터베이스가 이미 보장하는 동작을 중복 테스트하지 않는다.
- private helper나 내부 호출 순서보다 관찰 가능한 동작을 검증한다.

## 검증 강도

- 좁은 로직은 집중된 unit test를 우선한다.
- 경계를 넘는 사용자 핵심 흐름은 integration 또는 E2E 검증을 사용한다.
- 대표 surface가 CLI, API, 브라우저, 앱, 게임 runtime이면 위험에 비례해 실제 진입점을 실행한다.
- 고위험 변경, release gate, 보안 또는 데이터 변경은 독립 검증을 고려한다.
- 자동화 경로가 없으면 수동 검증과 남은 공백을 명확히 기록한다.

## 보고

- 실행한 정확한 명령과 관찰 결과를 구분해 적는다.
- 실패를 성공으로 요약하거나 실행하지 않은 테스트를 통과했다고 표현하지 않는다.
- 환경이나 권한 때문에 실행하지 못한 surface와 대체 검증의 한계를 남긴다.
